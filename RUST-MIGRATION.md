# Moving the desktop backend to Rust

Rust opens, plays, edits, and exports existing charts. In desktop
development, it owns preparation through lyrics review. Browser and desktop
share the Rust implementation for deterministic media, catalog, chart,
publication, and ZIP operations. Rust now owns BPM, pYIN, and Basic Pitch
execution. Python still owns post-approval state, Demucs, forced alignment,
and the default ASR evidence pipeline.

## Recommendation

Move the desktop workflow into Tauri's Rust backend and keep Python as a supervised inference worker. Rust should own imports, job state, library operations, media subprocesses, and UltraStar export. Keep the existing separation, transcription, alignment, and pitch implementations behind the worker boundary until individual replacements pass quality benchmarks.

If the immediate goal is an installer that runs on a clean machine, package the current backend first and give the built frontend an explicit API transport. That solves the deployment problem sooner. If the goal is to remove the desktop HTTP server and own the job lifecycle in Rust, carry out the staged migration below. Running without a system Python install is achievable through bundling. Removing the Python runtime entirely is a separate goal that depends on replacing the inference stack and deciding how to ship YouTube support.

## Starting architecture

The Tauri shell looks for `backend/main.py` relative to the checkout or executable. If nothing answers on port 8000, it tries to start Uvicorn using the repo venv or `python3`. The bundle config declares no backend sidecar, and the Solid frontend's relative `/api` requests use a proxy configured under Vite's development server. A packaged build needs both a backend distribution strategy and a working frontend transport. [Tauri startup](frontend/src-tauri/src/lib.rs) · [Bundle configuration](frontend/src-tauri/tauri.conf.json) · [Vite proxy](frontend/vite.config.ts)

Phase 1 imports media, extracts audio, separates vocals, detects BPM, and looks up lyrics. The job then waits for lyrics approval. Phase 2 creates or selects a lyric revision, drafts lyrics when needed, aligns canonical tokens, assigns pitch, and generates the chart. The editor can revise lyrics, lock word boundaries, edit notes, and compare SOFA and legacy results. English uses SOFA when its assets are available by default. Polish uses the legacy alignment path. An optional authenticated remote worker already has a validated alignment request and response contract. [Pipeline and API](backend/main.py) · [Job and result models](backend/models.py) · [Worker contract](backend/processing/alignment_worker.py)

## Implementation sequence

1. **Capture the baseline.** Record representative legacy job JSON and synthetic media fixtures, including interrupted jobs, English and Polish text, chart encodings, locks, continuation notes, and both alignment modes. Capture outputs at the chart, worker, and pitch boundaries. Agree on the first release target before building per-platform bundles.
2. **Proof of concept with one complete desktop flow.** Add a Tauri transport in `frontend/src/api.ts` for working-directory selection, external chart listing, editing, audio playback, and saving. Keep managed jobs on their existing path during development. Verify the external-chart flow in a packaged build with no checkout or Vite server. Scope media access to approved files, and exercise seek, edit, and save on an existing chart.
3. **Move managed jobs as a unit.** Add the Rust queue, app-data storage, native import, FFmpeg stages, and export. Extract a versioned Python CLI or worker protocol for separation, BPM, draft lyrics, alignment, and pitch. Send job/revision/run IDs and bounded local file references, return structured results and diagnostics, and capture worker stderr. Allow one owner for each job's state. Preserve the lyrics approval pause and resume from validated artifacts. Make migration idempotent and retain the original state and files for rollback. Exercise the existing remote alignment path with its authentication, audio-root mapping, and response validation. [Tauri sidecar packaging](https://v2.tauri.app/develop/sidecar/)
4. **Verify and switch the packaged desktop default.** Run local import and YouTube import through lyrics approval, processing, editing, restart, and export. Test worker startup errors, crashes, retry, and incomplete-output cleanup. Confirm audio seeking, old-library import, both alignment modes, and export in UltraStar Deluxe. Smoke-test every shipped target on a clean machine without a checkout, a running service on port 8000, or a system Python install. Keep the browser HTTP adapter available.
5. **Decide whether to remove the Python worker.** Benchmark Basic Pitch ONNX, then BPM or draft ASR where profiling or package size justifies it. Evaluate native SOFA, multilingual fallback alignment, and separation individually. Switch each stage only after parity and deployment tests. A Python-free desktop build is ready when every enabled local feature has a verified replacement or an explicitly supported remote path. Full offline processing requires local replacements.

## Acceptance gates

- **Deterministic outputs.** Compare chart text on fixed inputs and ZIP entry names and contents. Round-trip older jobs and verify job IDs, selected revisions, run IDs, locks, note overrides, and stem paths after restart. Check nested and root chart handling, path boundaries, and deletion scope.
- **Model quality.** Reuse `benchmark_alignment.py` and `benchmark_suite.py` with reference charts and matching audio. Compare canonical coverage, timing within one chart beat, boundary errors, exact MIDI agreement, and split-note accuracy per song and language. Use cached evidence or contours for component tests and real stems for end-to-end comparisons. Review outliers per song before accepting a replacement. [Benchmark implementation](backend/benchmark_alignment.py)
- **Deployment cost.** Compare installer and model-cache sizes, cold and warm stage time, peak memory, and import-to-export time on each intended platform. Rust reduces deployment or orchestration overhead when those are measured bottlenecks. FFmpeg and model inference need their own benchmarks.

## Investigation results

The Python suite in an isolated temporary copy produced **135 passes and one failure**. The current adaptive pitch-range test expected MIDI 68 and received 76. Running the selected tests from the checkout also hit three filesystem permission failures because the saved working directory was outside the sandbox. Those passed in the isolated run. Resolve or explicitly record the pitch baseline before using that test as a migration gate. No private reference files were present under `backend/benchmarks`, so model parity, speed, and packaged-runtime behavior remain unverified.
